How the referee works

Six steps, one number

The referee never asks what a person is doing. It asks how much of them changed since the last sample, and compares that against a cutoff that was measured rather than guessed.

Why body-fractions per second

A step taken two metres from the camera moves more pixels than the same step taken ten metres away. Cropping to the player's own box and resampling every crop to the same 96 × 96 window divides that out: the score is the fraction of that player that changed, so standing closer does not make you guiltier.

Why a fixed clock

A changed-pixel count does not grow linearly with how long you waited, so dividing by the frame gap does not make it fair across frame rates. Holding the measurement interval at 0.1 s does. A laptop at 60 fps and a phone at 24 judge the same motion over the same slice of time, and the benchmark measures the result: identical verdicts at 10 and 30 fps.

Tested

The scoring kernel in this tab and the one in the Python engine agree bit for bit on a shared set of golden 96 × 96 window pairs — identical frames, sensor noise, single pixels sitting exactly on the change threshold and one step past it, block shifts. The comparison is exact equality, not a tolerance, and you can run it here: re-run the fixtures in this browser. The verdict is written into the page title.

Watch the brightness

Sum the pixels in the player's box and call any change movement. It needs no model and no motion estimate at all. What it actually tracks is how many pixels the player covers: shrink them and it never fires, bring them closer and it fires on everybody. Move the size control and watch the two numbers stay level with each other — it flags frozen players and moving players at the same rate, which is another way of saying it is a coin flip.

Difference the whole frame

Subtract this frame from the last one, count the pixels that changed, and call it motion. On an empty room it works. Put one frozen player in a street scene and everybody else walking past is charged to them: the whole-frame score crosses its cutoff within a second and stays there for half the run, while the same player scored inside their own box reads exactly zero.

Estimate optical flow inside the box and threshold the raw pixel magnitude. Get the engine

Run it on your own footage

The browser arena is one half. The other is a Python package that runs the same rules over a webcam or a video file, with YOLO11n or weights-free HOG detection, and writes the benchmark every number on this page comes from. 

git clone https://github.com/safdar-hussain1/red-light-green-light-cv.git
cd red-light-green-light-cv
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[audio,analysis,dev]"

# play against your webcam
redlight play --source 0

# referee a video file, headless, and report
redlight play --source clip.mp4 --headless

# reproduce every number on this page
redlight benchmark --out reports/benchmark_results.json

# build this page from the results
redlight build-site

What is in the box

Detection, an IoU tracker with stable ids, the motion judge, the game state machine, a HUD, a synthesised chant, the benchmark harness, and this page's build. Tests cover all of it, including the parity suite that holds the browser judge to the Python one.
